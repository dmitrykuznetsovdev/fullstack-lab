## Где выполнять

- Условия остаются в папках этапов. Учебные решения добавляем в `exercises/solutions/00-workflow/`, `01-javascript/`, `02-browser/` соответственно.
- Этапы 3–7 развивают **одно** приложение в `exercises/solutions/app/`: `web/` для React + TypeScript + MobX + Rspack, затем `api/` для NestJS + TypeScript. Ученица создаёт эти папки по мере необходимости. Отдельный npm-проект для каждой маленькой задачи не нужен.
- На этапе 7 продолжаем ту же основу: один малый срез, ревью и выпуск в пределах двух заключительных недель. Обязательного переноса в `project/` или нового приложения нет. По будущей необходимости переносим код одной операцией с обновлением CI/инструкций; две расходящиеся копии не поддерживаем.
- Учебные заметки и подробные результаты проверок — `learning/<номер-задания>.md`. Статусы, уровень навыка и краткий журнал находятся только в [progress/README.md](../progress/README.md), с ссылками на заметки и PR. Если учеников станет несколько, сначала договоримся об отдельных каталогах или fork.

До первого запуска наставник помогает выбрать поддерживаемую LTS Node.js и закрепить её версию и команды. До первого npm-проекта добавляем `.gitignore` для зависимостей, сборки и локального окружения; lock-файл сохраняем. Готовой конфигурации приложения нет: настройка входит в задания. Используем вымышленные данные, локальную или изолированную учебную БД; собственные рабочие системы не трогаем.

## Формат сдачи каждого задания

Один небольшой PR с номером задания. Крупную задачу разрешено разбить на несколько PR с отдельной приёмкой. В описании:

1. Что пользователь теперь может сделать и какие правила приняты.
2. Где решение и как его запустить из чистой копии.
3. Что проверено: вход/действие → ожидаемый результат → фактический результат. Для дефекта — воспроизведение до исправления и проверка после.
4. Режим: что реализовал агент, что ученица объяснила, проверила и изменила сама, какие подсказки помогли и что осталось непонятным.
5. Короткая демонстрация и результат «Изменения на защите» из задания.

## AI и самостоятельность

Новый механизм ученица осваивает собственной малой пробой с прогнозом, запуском, объяснением и изменением; AI-наставник помогает вопросами и постепенными подсказками, без готовой изучаемой части и полного набора тестов. После подтверждения конкретного механизма на уровне задачи можно поручить агенту ограниченную реализацию, знакомую настройку и тесты. Ученица задаёт требования/ожидаемые проверки, читает diff, сопоставляет проверки с требованиями, запускает их и объясняет результат. На защите делает малое изменение без готовой генерации; документация разрешена. Новая часть смешанной задачи сначала проходит самостоятельную пробу. Непонятный сгенерированный код требует возвращения к малой пробе, а не принятия по зелёному CI. Процент ручной работы и срок без AI не назначаем. Все агенты загружают [скилл наставника](../.ai/skills/fullstack-mentor/SKILL.md).

Для намеренно ошибочных фрагментов сначала письменно предсказываем результат, затем запускаем. Готового исправления в каталоге нет. В каждом этапе читаем хотя бы один фрагмент кода, объясняем путь данных и изменяем условие; в задачах без исходного фрагмента читаем своё решение или diff напарника.

## Приёмка этапа

Все три задания приняты по своим критериям. Ученица объясняет существенный код, показывает обычный, граничный и ошибочный сценарии и выполняет небольшое изменение на защите. В едином прогрессе фиксируем доказательство и уровень: с пошаговой помощью / с подсказками / самостоятельно / переносит навык. Непройденный критерий записываем как следующий учебный шаг; состояние эпика следует из его заданий.

Для документов достаточно чтения и проверки diff. Для JS сначала используем `node:assert/strict`, с этапа 3 — Vitest для функций и MobX store, с этапа 4 — Jest + Supertest для NestJS. Rspack проверяется запуском dev и просмотром production-сборки, отдельно от `tsc --noEmit`. БД и HTTP проверяем интеграционно, критический браузерный сценарий на этапе 6 — Playwright. Сотня однотипных тестов не заменяет одну проверку опасного случая.

CI растёт после локального прохождения: одна JS-проверка на PR внутри 1.3 → tsc/Vitest/Rspack build на этапе 3 → проверка типов/NestJS build/Jest-Supertest на этапе 4 → интеграционные проверки с изолированной PostgreSQL на этапе 5 → весь набор и Playwright на этапе 6. Конфигурацию ученица создаёт по мере заданий. Готовый workflow `.github/workflows/checks.yml` — только автопроверка наставника (ниже); свой workflow в 1.3 ученица создаёт отдельно. Локальный тест, реальный журнал CI, сборка, просмотр браузера и чистый выпуск — разные доказательства. Малые части не добавляют ID и не заменяют полную приёмку/защиту задания.

## Автопроверка и сверка прогресса

У части заданий есть `checks/<ID>.test.mjs` в папке этапа: это проверка **наставника** по контракту из условия. Пока решения нет, проверка пропускается. Запуск всех: `node --test "exercises/*/checks/*.test.mjs"`, одного: `node --test "exercises/*/checks/1.1.test.mjs"`. Зелёная автопроверка подтверждает только поведение кода: собственные проверки, объяснение и «Изменение на защите» остаются обязательными. Не копировать автопроверку в своё решение.

`node scripts/progress.mjs` показывает начатые задания и результат автопроверки; с `--check` падает при ошибках учёта [прогресса](../progress/README.md) (завышенный статус, статус без доказательства); отставание прогресса от решения — лишь предупреждение. Обе команды выполняются в CI на каждом PR. Сценарии наставника `lesson`, `check`, `defend`, `review` и роль экзаменатора лежат в [.ai/skills/fullstack-mentor/workflows/](../.ai/skills/fullstack-mentor/workflows/) и работают в любом агенте (Codex, Claude Code); в Claude Code они вызываются как `/lesson`, `/check`, `/defend`, `/review`.
