## 3.1 — Типы и граница внешних данных

**Задача.** Включить строгую проверку TypeScript, описать `Session` с полями `id`, `title`, `freePlaces`, перенести фильтрацию 1.1 в TypeScript. Написать `parseSession(value: unknown): Session`: принимать непустой строковый id, название 1–80 символов после trim, целое `freePlaces >= 0`. При неверных данных выбрасывать `Error` с понятным сообщением. Дополнительные поля игнорировать.

Сначала разобрать типы функций и массивов, затем narrowing и проверку внешних данных. Закрепить команды проверки типов и Vitest для чистых функций. Новый механизм ученица подтверждает собственной пробой с подсказками наставника; знакомую часть функции или тестов можно ограниченно делегировать после подтверждения по двум режимам.

**Сдать:** тип, функцию разбора, типизированную фильтрацию и тесты; версию Node.js, lock-файл и команды в README решения.

**Приёмка:**
- Валидный объект принимается, `null`, отсутствующее поле, `'2'` вместо числа, `NaN`, дробь и отрицательное число отклоняются.
- Нет обхода проверки через `any`, `as Session` или отключение строгого режима.
- Ученица объясняет, почему тип не проверяет JSON во время выполнения, и различает `unknown` и уже проверенный `Session`.
- Проверка типов выявляет несовместимое присваивание в отдельной временной пробе; тест выявляет неверное правило во время выполнения. Пробы не остаются в рабочем коде.

**Изменение на защите:** добавить обязательное поле `status: 'open' | 'closed'` в отдельной пробе, затем показать, какие места обнаружил компилятор. Основной контракт менять только отдельным согласованным заданием.

## 3.2 — Компоненты, сборка и общий store

**Задача.** Перенести список, фильтр и форму этапа 2 в React, сохранив их правила. Выполнять по трём небольшим шагам с разбором каждого diff:

1. Настроить React + TypeScript на Rspack: точка входа, HTML, обработка TSX и CSS, dev server и production-сборка. Начать с минимального экрана, разобраться в конфигурации до переноса формы. Использовать Rspack напрямую, чтобы увидеть настройку сборщика; включить `isolatedModules` для пофайлового преобразования TypeScript.
2. Выделить компоненты формы, фильтра и списка, пройти props, события и локальное состояние React. Показать работающий вариант с одним владельцем данных.
3. Перенести общий список и применённый фильтр в один MobX store. Разобрать observable, computed и action через `makeAutoObservable` или явные аннотации без MobX-декораторов. Подключить функциональные компоненты через `observer` из `mobx-react-lite`. Черновик формы можно оставить локальным React state, объяснив границу.

Переходить к следующей части после наблюдаемого результата предыдущей:

| Часть 3.2 | Малый результат и промежуточная приёмка |
| --- | --- |
| Rspack и минимальный экран | Из чистой копии работают dev и build; production JS/CSS просмотрены локально, сервер остановлен. Отдельный `tsc --noEmit` выявляет временную ошибку типов; ученица объясняет entry/output и преобразование TSX/CSS |
| React до MobX | Форма, фильтр и список работают с одним владельцем данных; ученица объясняет props, события, state и ключи, самостоятельно меняет малое условие. Эта версия сохранена в истории той же основы |
| MobX и наблюдающий UI | Устойчивый store, action/computed/observer проверены тестом и действием в UI; callback сохраняет контекст. Потеря и возврат подписки воспроизведены и объяснены |

Части не получают новых ID или статусов. Всё 3.2 принимается только после полной приёмки ниже и самостоятельного изменения на защите. После локального прохождения расширить начатый в 1.3 CI командами проверки типов, Vitest и Rspack build; зелёный CI не заменяет просмотр production-сборки и действия в UI.

Отфильтрованный список вычисляется из данных и фильтра; отдельную обновляемую копию не храним. Store имеет устойчивый экземпляр на время работы интерфейса; тесты создают независимые экземпляры. Проверить передачу метода store как callback и сохранение его контекста. Промежуточный React-вариант показать до добавления MobX, сохранив обе стадии в истории PR без двух копий приложения.

**Сдать:** интерфейс, свою конфигурацию Rspack, команды dev/build/typecheck/test и схему «событие → action → observable → computed → observer → UI».

**Приёмка:**
- Сохранены проверки ввода, работа клавиатуры, адаптивность и пустой результат; элементы имеют устойчивые ключи по id.
- Добавление через action обновляет список и computed при действующем фильтре; правила проверены тестами store и продемонстрированы в UI.
- В отдельной пробе убрать `observer` у компонента, читающего store напрямую, и воспроизвести отсутствие его обновления при action без другого React-render. Вернуть подписку и повторить действие; объяснить место чтения observable.
- Из чистой копии запускается dev server, создаётся production-сборка; её результат просмотрен через локальный статический сервер, затем сервер остановлен. Проверены загрузка JS/CSS и основные действия формы.
- Ученица показывает entry/output, обработку TSX/CSS и режим сборки. Ошибка типов проверяется отдельной командой `tsc --noEmit`: успешное преобразование TSX сборщиком само по себе не подтверждает корректность типов.
- Vitest запускается отдельно для функций и store; его прохождение не выдаётся за проверку конфигурации Rspack.

**Изменение на защите:** добавить удаление занятия по id через action и проверить пересчёт списка; объяснить, где изменяются данные и почему не нужно отдельно менять computed.

## 3.3 — Медленный ответ не должен побеждать новый

**Подготовка внутри задания.** На другом вымышленном объекте объяснить отличие JSON-строки от JS-значения, разбор и проверку данных во время выполнения. По [чтению JSON/fetch](../../docs/reading.md#подготовка-механизма-и-малая-проверка) сделать собственную малую локальную пробу запроса: ожидание, статус HTTP, разбор JSON, отказ сети и некорректные данные. HTTP-ошибка и отклонённый Promise — разные случаи; получить `404` само по себе не означает отказ `fetch`. Локальный ответ можно подготовить с наставником, внешний API не обязателен. В самом 3.3 остаётся управляемая подмена ниже; реальный backend подключается в 4.2.

**Задача.** Добавить поиск по названию с загрузкой при нажатии кнопки. Написать локальную подмену API `searchSessions(query)`: `'ша'` возвращает Шахматы через 600 мс, `'му'` — Музыку через 100 мс, `'ошибка'` отклоняет Promise, неизвестный запрос возвращает пустой список. Backend пока не нужен. Перед выдачей store данные проходят проверку 3.1.

Намеренно наивная идея для воспроизведения: каждый ответ без проверки записывать в store. Запустить поиск `'ша'`, сразу затем `'му'`. Требование: интерфейс соответствует **последнему запущенному запросу**, включая ошибки и индикатор загрузки. Поздний старый ответ ничего не меняет.

Загрузку и её результат хранить в MobX store; не дублировать их в React state. Разобрать, почему продолжение после `await` требует отдельной action-границы, и выбрать `runInAction` либо отдельные actions. Настроить `enforceActions: 'always'`, проверить диагностику и обновления. Если используется reaction/autorun, объяснить необходимость и освобождение подписки; добавлять их ради самого факта наличия не нужно.

**Сдать:** состояния `loading / success / empty / error`, повторную попытку и проверки гонки store. Контролируемые Promise или fake timers предпочтительнее реального ожидания.

**Приёмка:**
- Второй ответ пришёл первым: на экране остаётся Музыка и после завершения первого.
- Старые ошибка и успешный ответ не меняют новый результат; старое завершение не снимает новый loading.
- Ошибка отличается от пустого результата; повторная попытка восстанавливает работу; некорректные внешние данные не выдаются за успех.
- После асинхронного ответа observable меняются внутри actions; нет предупреждений о нарушении выбранного режима MobX. Проверена и успешная, и ошибочная ветка.
- Ученица объясняет идентификацию/отмену запроса и что происходит при уходе с экрана; старый запрос не изменяет новый экземпляр store. Собственные таймеры и подписки освобождаются.

**Изменение на защите:** сделать первый запрос ошибочным и доказать, что его поздняя ошибка не заменяет успешный второй результат.
