## 3.1 — Типы и граница внешних данных

**Задача.** Описать `Session` с полями `id`, `title`, `freePlaces`, перенести фильтрацию 1.1 в TypeScript. Написать `parseSession(value: unknown): Session`: принимать непустой строковый id, название 1–80 символов после trim, целое `freePlaces >= 0`. При неверных данных выбрасывать `Error` с понятным сообщением. Дополнительные поля игнорировать.

**Сдать:** тип, функцию разбора, типизированную фильтрацию и тесты.

**Приёмка:**
- Валидный объект принимается, `null`, отсутствующее поле, `'2'` вместо числа, `NaN`, дробь и отрицательное число отклоняются.
- Нет обхода проверки через `any`, `as Session` или отключение строгого режима.
- Ученик объясняет, почему тип не проверяет JSON во время выполнения, и различает `unknown` и уже проверенный `Session`.

**Изменение на защите:** добавить обязательное поле `status: 'open' | 'closed'` в отдельной пробе, затем показать, какие места обнаружил компилятор. Основной контракт менять только отдельным согласованным заданием.

## 3.2 — Перенести интерфейс на компоненты

**Задача.** Перенести список, фильтр и форму этапа 2 в React, сохранив их правила. Выделить компоненты формы, фильтра и списка; определить владельца состояния. Список после фильтрации вычисляется из данных и фильтра, а не хранится отдельной несогласованной копией.

**Сдать:** интерфейс и схему «кто хранит состояние → кто получает props → кто сообщает об изменении».

**Приёмка:**
- Сохранены проверки ввода, работа клавиатуры, адаптивность и пустой результат.
- Добавление и фильтрация работают совместно; элементы имеют устойчивые ключи по id.
- Тестами проверены правила фильтрации/валидации; интерфейс продемонстрирован вручную.
- Ученик объясняет каждое состояние и может показать лишнее производное значение, которое не нужно хранить.

**Изменение на защите:** добавить удаление одного занятия по id; объяснить передачу события из строки списка владельцу данных.

## 3.3 — Медленный ответ не должен побеждать новый

**Задача.** Добавить поиск по названию с загрузкой при нажатии кнопки. Написать локальную подмену API `searchSessions(query)`: `'ша'` возвращает Шахматы через 600 мс, `'му'` — Музыку через 100 мс, `'ошибка'` отклоняет Promise, неизвестный запрос возвращает пустой список. Backend пока не нужен.

Намеренно наивная идея, которую требуется проверить: каждый ответ без проверки записывать в состояние. Запустить поиск `'ша'`, сразу затем `'му'`. Реализовать правило: интерфейс соответствует **последнему запущенному запросу**, включая ошибки и индикатор загрузки. Поздний старый ответ ничего не меняет.

**Сдать:** состояния `loading / success / empty / error`, повторную попытку и проверку гонки. Контролируемые Promise или fake timers предпочтительнее тестов с реальным ожиданием.

**Приёмка:**
- Второй ответ пришёл первым: на экране остаётся Музыка и после завершения первого.
- Старые ошибка и успешный ответ не меняют новый результат; старое завершение не снимает новый loading.
- Ошибка отличается от пустого результата; повторная попытка восстанавливает работу.
- Ученик объясняет выбранную отмену/идентификацию запроса и жизненный цикл компонента.

**Изменение на защите:** сделать первый запрос ошибочным и доказать, что его поздняя ошибка не заменяет успешный второй результат.
