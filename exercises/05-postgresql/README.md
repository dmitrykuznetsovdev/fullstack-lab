# Этап 5. SQL, PostgreSQL и целостность

[Каталог и правила сдачи](../README.md) · [Далее: надёжность](../06-reliability/README.md)

**До старта:** этап 4; SELECT/INSERT/UPDATE, ключи, транзакции. Использовать отдельную локальную учебную БД и отдельную БД для тестов. Наставник помогает с установкой PostgreSQL или контейнером; пароли находятся только в локальном окружении. Решение продолжает `exercises/solutions/app/api/`.

## 5.1 — Данные переживают перезапуск

**Задача.** Перенести хранение API в PostgreSQL. Минимальная схема: `users(id)`, `sessions(id,title,capacity)`, `bookings(id,user_id,session_id,status)`. `capacity >= 0`; статус — `active/cancelled`; внешние ключи обязательны. Активная запись пары пользователь/занятие может быть только одна, отменённых — несколько. Свободные места вычисляются как вместимость минус активные записи.

Начальные пользователи и занятия задаются отдельным seed для учебной среды, с вместимостью 0/2/3. API пока создаёт только активные записи. Подготовить версионируемую SQL-миграцию и инструкции запуска с нуля. Не использовать ORM для первых операций.

**Сдать:** миграцию, seed, слой запросов и интеграционные тесты на PostgreSQL.

**Приёмка:**
- Созданная запись остаётся после перезапуска сервера и БД; схема воспроизводится в пустой тестовой БД.
- БД отвергает неизвестные внешние ключи, отрицательную вместимость, неверный статус и повтор активной пары.
- Все значения в SQL передаются параметрами; кавычка в строке не меняет структуру запроса.
- Контракт 4.1 сохранён для известных пользователей; неизвестный пользователь получает `400 INVALID_INPUT`.
- Перед сбросом тестов команда проверяет, что подключена именно тестовая БД; рабочие БД не используются.

**Изменение на защите:** добавить nullable-описание занятия отдельной миграцией, сохранить существующие данные, показать отличие `NULL` от пустой строки.

## 5.2 — JOIN, агрегация и цена запроса

**Задача.** Получить занятия с числом активных записей и свободных мест одним SQL-запросом. В тестовых данных: занятие без записей, с двумя активными, только с отменёнными. Запрос должен возвращать все занятия. Разобрать ошибочный подход: `INNER JOIN` и фильтр `WHERE bookings.status = 'active'` исключают часть занятий.

**Сдать:** запрос, интеграционные проверки, краткую заметку о JOIN/агрегации и один план `EXPLAIN` на вымышленных данных.

**Приёмка:**
- Пустые и только отменённые занятия имеют 0 активных записей; число мест посчитано верно.
- Нет отдельного запроса за числом записей для каждой строки списка.
- Ученик объясняет, почему условие соединения и фильтр результата не всегда взаимозаменяемы.
- С наставником прочитан эквивалентный пример Prisma/Drizzle из официальной документации выбранной версии: какие SQL-операции нужны, где остаётся транзакция. Подключать ORM в проект необязательно; вывод не основан на предположении, что ORM автоматически защищает все правила.

**Изменение на защите:** добавить условие «показывать только занятия хотя бы с одним свободным местом» и проверить полностью занятое занятие.

## 5.3 — Два запроса на последнее место

**Задача.** Для занятия с вместимостью 1 одновременно отправить два `POST /bookings` от разных существующих пользователей. Найти, почему раздельные «прочитать остаток → вставить запись» допускают переполнение, и выбрать защиту на уровне транзакции/блокировки в PostgreSQL.

**Сдать:** интеграционный тест с двумя независимыми соединениями и согласованным одновременным стартом, исправление и описание границы транзакции. Обычный последовательный тест не доказывает защиту от гонки. Воспроизведение исходного дефекта можно управлять барьером между чтением и вставкой в тестовой пробе; барьер не должен оставаться в рабочем пути.

**Приёмка:**
- Ровно один ответ `201`, второй — `409 NO_PLACES`; в БД одна активная запись, свободных мест 0.
- Проверен конкурентный повтор от одного пользователя: одна запись, второй ответ `ALREADY_BOOKED`.
- Ошибка внутри транзакции откатывает изменения; соединения возвращаются в пул.
- Защита работает через независимые соединения, не опирается только на флаг в памяти Node.js.

**Изменение на защите:** вместимость 2 и три участника: две успешные записи, один отказ. Объяснить, какие строки конкурируют и почему.
