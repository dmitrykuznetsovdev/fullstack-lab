# Этап 7. Совместный продукт и самостоятельность

[Каталог и правила сдачи](../README.md) · [Учебный план](../../README.md)

**До старта:** этап 6 и согласованный выбор предметной области. Сервис записи — кандидат, а не автоматически выбранный продукт. Сохраняем React + TypeScript + MobX + Rspack и NestJS + TypeScript. Используем вымышленные данные до отдельного решения о реальном запуске. Место приложения остаётся `exercises/solutions/app/`: продолжаем основу этапов 3–6. Обязательного переноса в `project/` и нового приложения нет; по дальнейшей необходимости перемещаем код одной операцией с обновлением путей CI/инструкций, без второй копии. Малый предметный сценарий обсуждаем после этапа 3.

Два заключительных учебных цикла завершают существующую основу: на 25-й неделе — один малый срез 7.1 и ревью заранее подготовленного человеком PR 7.2; на 26-й — одна ограниченная правка по обратной связи и чистый выпуск/защита 7.3. Большая продуктовая итерация идёт после первой итерации курса; при нехватке времени критерии честно остаются незакрытыми, по дате их не принимаем. Ученица владеет своей задачей; человек-наставник может вести отдельную часть совместного продукта и ревью. AI помогает освоить новое собственной малой пробой; ограниченная реализация подтверждённого допускается по [двум режимам](../../.ai/skills/fullstack-mentor/SKILL.md) с требованиями, чтением diff, проверками и объяснением. Ни один участник не подменяет её самостоятельную защиту. Состояние и результаты фиксируем в [едином прогрессе](../../progress/README.md).

## 7.1 — Самостоятельная задача через весь стек

**Задача.** Провести короткий разговор с доступным потенциальным пользователем о проблеме расписания, записать обезличенные выводы и выбрать один сценарий. Если пользователь пока недоступен, наставник играет заказчика; это прямо отмечается как учебная симуляция.

Базовый сценарий: организатор закрывает занятие для новых записей. Добавить `status: open/closed` отдельной миграцией; существующие занятия остаются открытыми. Действующие записи сохраняются, отмена разрешена; новые записи на закрытое занятие запрещены сервером (`409 SESSION_CLOSED`). Изменять статус может только организатор: без сессии `401`, участнику `403`, неизвестный id `404`. До кода описать контракт endpoint и приоритет ошибок при пересечении правил.

**Сдать:** локальную карточку задачи с критериями (или Issue, если этот процесс выбран), план из нескольких шагов, PR с миграцией/API/UI/проверками и демонстрацию. При другой теме сохранить сопоставимые требования: сохранение данных, серверное бизнес-правило и права.

**Приёмка:**
- UI объясняет закрытый статус; прямой запрос участника не обходит запрет.
- Проверены сохранение старых записей, отмена и повторное открытие.
- Отдельно рассмотрена гонка закрытия и записи: операции сериализованы по занятию; запись, завершившаяся до закрытия, допустима, после закрытия — нет.
- Ученик сам объясняет путь от требования до миграции и теста, фиксирует помощь наставника.
- Объяснены затронутые MobX actions/computed, NestJS controller/service/guard и сборка; проверки подтверждают весь сценарий, а не только отдельный метод.

**Изменение на защите:** добавить необязательную причину закрытия до 200 символов и описать, какие слои затронет изменение; реализовать ограниченный согласованный кусок.

## 7.2 — Прочитать PR напарника

**Задача.** Человек-наставник готовит отдельный небольшой учебный PR на NestJS: `GET /me/bookings`, который должен возвращать только записи вошедшего пользователя. Для воспроизводимой пробы исходная версия возвращает активные записи всех пользователей. AI помогает ученице читать diff и искать проверку, не выдаёт исправление за неё. Такой PR не сливать и не публиковать в рабочую среду до исправления.

Ученик сначала читает diff и описывает поведение, затем находит нарушение на двух вымышленных пользователях. Оставляет предметное замечание «действие → фактический результат → нарушенное правило» и добавляет проверку. Напарник исправляет; ученик повторяет проверку. Не переписывать весь модуль ради стилистических предпочтений.

**Сдать:** ссылку на PR, воспроизведение, регрессионную проверку и краткую карту обработчик → запрос → данные → ответ.

**Приёмка:**
- Проверка падает на исходной реализации и проходит после исправления.
- Без входа — `401`; пользователь A не видит записи B; отсутствие собственных записей — `200 []`.
- Разделены существенная ошибка и необязательные предложения по стилю.
- Автор и ревьюер объясняют исправление; дефектная ветка не попала в выпуск.

**Изменение на защите:** добавить фильтр статуса `active/cancelled` и проверить, что он не ослабил фильтр владельца.

## 7.3 — Выпуск, обратная связь и пробное собеседование

**Задача.** Собрать учебный выпуск с инструкцией и описанием ограничений, провести демонстрацию напарнику/пользователю, записать обратную связь и исправить одну конкретную проблему отдельным PR. Повторить проверку из чистой копии. Подготовить описание проекта для портфолио без выдуманного коммерческого опыта.

**Сдать:** release notes с commit/tag, способ доступа к демонстрации (локальная инструкция допустима), результаты проверок и `learning/7.3.md` с оставшимися пробелами. Платная или публичная инфраструктура не обязательна.

**Приёмка:**
- Другой человек проходит просмотр, запись и отмену по инструкции; права и конкурентная запись проверены.
- Указаны авторство частей, использование AI, ограничения и что именно проверялось: CI, локальный стенд или публичная среда.
- Ученик за 10–15 минут объясняет одну задачу, один дефект, модель данных и одну неудачную гипотезу.
- По трём актуальным начальным вакансиям составлена таблица «требование → доказательство в проекте → пробел»; отсутствие навыка обозначено честно.

**Изменение на защите:** наставник выбирает одно небольшое новое условие в знакомом модуле; ученик уточняет его, меняет код и проверяет результат без генерации готового ответа. Если не справился, формулируем следующую учебную задачу.
