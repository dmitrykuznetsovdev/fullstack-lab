## 4.1 — API по явному контракту

**Задача.** Сделать API с исходными занятиями `a/b/c` из этапа 1. Считать их `freePlaces` начальной вместимостью; бронирование занимает ровно одно место. Идентификаторы участников — вымышленные непустые строки. Поля записи: `id`, `sessionId`, `userId`, `status: 'active'`.

| Запрос | Ожидаемое поведение |
| --- | --- |
| `GET /sessions` | `200`, массив с текущими свободными местами; пустой массив допустим |
| `POST /bookings` с `{sessionId, userId}` | `201`, новая запись; оба поля — непустые строки |
| Неверное тело | `400`, `{error:{code:'INVALID_INPUT',message:...}}` |
| Неизвестное занятие | `404`, код `SESSION_NOT_FOUND` |
| Повторная активная запись этого пользователя на занятие | `409`, код `ALREADY_BOOKED` |
| Нет мест | `409`, код `NO_PLACES` |

При повторе проверять `ALREADY_BOOKED` до проверки свободных мест. Неверный запрос не меняет состояние. Не возвращать stack trace. Автоматические проверки можно выполнять через Fastify `inject`, без постоянно работающего сетевого сервера.

**Сдать:** API, контракт и проверки всех строк таблицы.

**Приёмка:** первая запись на `b` уменьшает число мест с 2 до 1; повтор тем же пользователем не уменьшает его; второй участник занимает последнее место; третий получает `NO_PLACES`. Перезапуск сбрасывает данные — это явно описано. Ученик прослеживает тело запроса до изменения состояния.

**Изменение на защите:** добавить `GET /sessions/:id`, договориться о форме ответа и проверить известный/неизвестный id.

## 4.2 — Подключить браузер к серверу

**Задача.** Заменить подмену API в интерфейсе реальным `GET /sessions`, добавить кнопку записи. Для локальной практики выбрать одного фиктивного участника. Настроить dev proxy или ограниченный CORS с наставником, записать команды запуска двух частей.

**Сдать:** демонстрацию списка и записи, таблицу проверки ответов и сбоев. Поиск можно выполнять локально по загруженному списку; поискового endpoint в 4.1 нет.

**Приёмка:**
- Видны загрузка, успех, пустой результат и ошибка; повторная загрузка работает.
- При записи кнопка заблокирована до завершения запроса, после успеха места перечитываются с сервера.
- `409` показан как конфликт записи; остановленный сервер — как ошибка соединения; кнопка снова доступна после сбоя.
- Снятие блокировки кнопки не отменяет серверную защиту от повторной записи.
- В Network ученик показывает метод, тело, статус и ответ одного успешного и одного ошибочного запроса.

**Изменение на защите:** имитировать `500` и доказать, что UI не показывает ложный успех. Затем вернуть нормальное поведение сервера.

## 4.3 — Исправить обработчик из чужого кода

**Задача.** В отдельной пробе воспроизвести дефекты фрагмента. В нормальном API контракт ошибок остаётся из 4.1.

```js
async function createBooking(request, reply) {
  try {
    const result = repository.save(request.body);
    return reply.code(201).send(result);
  } catch (error) {
    return reply.code(200).send({ ok: false });
  }
}
```

Подмена `repository.save` через Promise либо возвращает запись, либо отклоняется `Error('storage unavailable')`. С наставником разобраться, что делает Fastify с переданным Promise в выбранной версии; не угадывать сетевой результат только по чтению кода. Требование: успешное сохранение — `201` с записью, сбой — `503` и код `STORAGE_UNAVAILABLE`, без текста внутренней ошибки в ответе.

**Сдать:** воспроизведение, исправление и тесты обработчика через реальное HTTP-поведение Fastify (`inject` допустим).

**Приёмка:** зафиксированы фактические статусы/тела до и после; ошибка асинхронного сохранения обрабатывается в нужной границе, отсутствует ложный `2xx`; внутреннее сообщение остаётся в серверной диагностике. Ученик объясняет `await` и `try/catch`.

**Изменение на защите:** задержать сохранение и показать, что подтверждение не приходит раньше успешного завершения.

**Необязательное расширение после этапа 5:** повторить один endpoint в NestJS в отдельной пробе, сравнить валидацию и обработку ошибок. Это знакомство для вакансий, не миграция всего приложения.
