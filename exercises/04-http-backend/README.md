**До старта:** этап 3; разобрать HTTP-методы, JSON, коды ответа и асинхронность до написания контроллера. NestJS + TypeScript в `exercises/solutions/app/api/`, строгая проверка типов. Хранение в памяти, локальная учебная среда; аутентификации ещё нет, поле пользователя не доказывает личность. Клиент показывает расписание и создаёт записи, создание занятий остаётся локальной практикой этапа 3.

Выбрать совместимые версии по официальной документации, сохранить lock-файл и команды. Стандартный HTTP-адаптер NestJS достаточен; отдельный курс адаптера не нужен. Backend-проверки — Jest, `@nestjs/testing` и Supertest; Rspack собирает только frontend. Команды проверки типов, сборки и тестов API описать отдельно.

Перед DI разобрать class, constructor и типизированный метод на небольшой пробе. В браузере и отдельном HTTP-клиенте показать запрос/ответ до разбора декораторов. Дополнительные сценарии для обсуждения — [короткие разборы](../../examples/README.md).

**Подготовка Node.js внутри 4.1.** Сначала сделать две конечные локальные пробы на другом сюжете; они не получают отдельных ID. Предсказать порядок событий при асинхронном ожидании и при синхронной работе, которая занимает event loop. Ограничить блокирующую работу длительностью не более секунды и наблюдать, когда может выполниться другой callback. Сравнивать причину и порядок, без требования одинаковых миллисекунд и нагрузочного тестирования. Не выполнять бесконечный цикл и не переносить пробу в рабочий сервер.

Затем создать маленький вымышленный файл в собственном временном каталоге и прочитать его синхронным и асинхронным API Node.js; проверить отсутствие файла и обработку ошибки. Объяснить, где ждёт программа и где она занята работой; маленький файл не обязан показать измеримую разницу скорости. Закрыть открытые своей пробой ресурсы, удалить её файлы. [Официальное чтение](../../docs/reading.md#подготовка-механизма-и-малая-проверка) ограничено IO и этим наблюдением; libuv, worker threads и профилирование пока не нужны.

Проверить жизненный цикл своего процесса: запуск с нужной конфигурацией, понятная диагностика ошибки запуска/занятого порта, остановка и освобождение порта. Занятый порт воспроизводить вторым собственным процессом или выбрать другой порт; чужой процесс не завершать. В HTTP-тестах Nest-приложение закрывается через `app.close()` даже после неуспешной проверки; если используются shutdown hooks по сигналу, их явно включают и проверяют по документации выбранной версии. Освобождение будущего пула БД добавляется на этапе 5.

## 4.1 — API по контракту: module, controller, service

**Задача.** Создать API с исходными занятиями `a/b/c` из этапа 1. Считать их `freePlaces` начальной вместимостью; бронирование занимает ровно одно место. Участники — вымышленные непустые строки. Поля записи: `id`, `sessionId`, `userId`, `status: 'active'`.

Разбить работу: модуль с `GET`, provider с данными в памяти, затем `POST` с DTO и валидацией. Controller отвечает за HTTP-вход/выход, service — за бизнес-правила. Зарегистрировать providers в module и получить зависимости через DI. Наставник помогает прочитать ошибку незарегистрированной зависимости в отдельной пробе; ученица восстанавливает регистрацию.

Малые результаты: сначала наблюдаемый `GET /sessions` и объяснённая регистрация/инъекция; затем `POST` с DTO, изменением состояния и отказом неверному телу; затем единая форма ошибок и проверки всех строк таблицы через HTTP. После каждого результата прочитать diff и объяснить путь данных, сохраняя одну основу. Это промежуточная приёмка, всё 4.1 закрывается по полной приёмке и защите. После локального прохождения расширить существующий CI отдельными командами проверки типов API, NestJS build и Jest/Supertest; frontend-проверки сохраняются.

| Запрос | Ожидаемое поведение |
| --- | --- |
| `GET /sessions` | `200`, массив с текущими свободными местами; пустой массив допустим |
| `POST /bookings` с `{sessionId, userId}` | `201`, новая запись; оба поля — непустые строки после trim |
| Неверное тело, включая лишние поля | `400`, `{error:{code:'INVALID_INPUT',message:...}}` |
| Неизвестное занятие | `404`, код `SESSION_NOT_FOUND` |
| Повторная активная запись этого пользователя на занятие | `409`, код `ALREADY_BOOKED` |
| Нет мест | `409`, код `NO_PLACES` |

При повторе проверять `ALREADY_BOOKED` до свободных мест. Неверный запрос не меняет состояние. DTO должен быть проверяемым во время выполнения классом, а не только TS-интерфейсом. Настроить `ValidationPipe`, явно определить политику лишних полей и обработки пробелов; приведение произвольного значения к строке не заменяет проверку. Через exceptions/filter или настройку ошибки pipe привести ответы к указанной форме; стандартный ответ NestJS сам по себе не считается этим контрактом. Не возвращать stack trace.

**Сдать:** API, контракт и проверки таблицы. Нарисовать отдельно регистрацию module → controllers/providers и путь HTTP-запрос → pipe → controller → service → provider → ответ: module не является обработчиком запроса.

**Приёмка:**
- Первая запись на `b` уменьшает места с 2 до 1; повтор не уменьшает их; второй участник занимает последнее место; третий получает `NO_PLACES`.
- Отклоняются отсутствующие поля, числа, пустые/пробельные строки и лишний ключ; проверки выполняются прямым HTTP-запросом, независимо от UI.
- Есть unit-проверки service и HTTP-проверки через Nest-приложение из `TestingModule` и Supertest. Pipes/filters настроены так же, как при обычном запуске; тест одного метода controller не доказывает HTTP-контракт.
- Перезапуск сбрасывает данные — это описано. Приложение и тестовые ресурсы закрываются после проверки.
- Ученица объясняет provider scope по умолчанию, регистрацию/инъекцию и отличие компиляции DTO-типа от реальной проверки тела.

**Изменение на защите:** добавить `GET /sessions/:id`, договориться о форме ответа и проверить известный/неизвестный id.

## 4.2 — Подключить MobX-клиент к NestJS

**Задача.** Заменить подмену API реальным `GET /sessions`, добавить кнопку записи. Выбрать одного фиктивного участника. Настроить dev proxy Rspack либо ограниченный CORS в NestJS с наставником; записать команды двух частей. Общие данные и состояние запросов остаются в MobX store, компоненты показывают их через `observer`.

**Сдать:** демонстрацию списка и записи, таблицу ответов/сбоев и схему браузер → store → HTTP → DTO/pipe → controller → service → ответ → action → UI. Поиск можно выполнять локально: поискового endpoint в 4.1 нет.

**Приёмка:**
- Видны загрузка, успех, пустой результат и ошибка; повторная загрузка работает.
- При записи кнопка заблокирована до завершения запроса, после успеха места перечитываются с сервера; правило последнего запроса из 3.3 сохранено.
- `409` показан как конфликт; остановленный сервер — как ошибка соединения; кнопка снова доступна после сбоя. Обновления store после `await` остаются внутри actions.
- Снятие блокировки UI не отменяет серверную защиту от повторной записи.
- В Network ученица показывает метод, тело, статус и ответ успешного и ошибочного запроса; объясняет адрес API при dev proxy и просмотре production-сборки.

**Изменение на защите:** имитировать `500` и доказать, что UI не показывает ложный успех. Затем вернуть нормальное поведение сервера.

## 4.3 — Асинхронная ошибка и подмена provider

**Задача.** В отдельной пробе воспроизвести поведение намеренно ошибочного метода Nest-контроллера. Это фрагмент для чтения, не готовая реализация API. Ученица добавляет нужные импорты, тестовый module, DTO и внедряемый repository provider; маршрут пробы — `/probe/bookings`. В основном API сохраняется контракт 4.1.

```ts
@Post()
@HttpCode(201)
async create(@Body() input: CreateBookingDto) {
  try {
    return this.repository.save(input);
  } catch (error) {
    return { ok: false };
  }
}
```

В `TestingModule` подменить repository через DI: успешный Promise возвращает запись, отклонённый Promise выдаёт `Error('storage unavailable')`; отдельно проверить синхронное исключение. Предсказать ответ, затем измерить реальный статус/тело через Nest и Supertest. Разобрать, какие ошибки попадают в локальный `catch`, какие — в слой исключений NestJS, и почему возвращённый объект не является HTTP-ошибкой.

Требование после самостоятельного исправления: успех — `201` с записью, сбой зависимости — `503` с кодом `STORAGE_UNAVAILABLE`, внутренний текст остаётся в серверной диагностике. Ошибки валидации и бизнес-правил не превращаются в ошибки хранения; их контракт сохранён. Подмена применяется только в тесте, рабочая проверка ошибок не отключается.

**Сдать:** фактические статусы/тела до и после, минимальное исправление и регрессионные HTTP-проверки.

**Приёмка:**
- Проверены успешное сохранение, асинхронный отказ и синхронное исключение; ни один отказ не выдаётся за успешный `2xx`.
- Ученица объясняет `await`, границу `try/catch` и exceptions/filter; неизвестные ошибки не маскируются произвольным успехом.
- Тестовая подмена provider не требует изменения production module; приложение закрывается после тестов.

**Изменение на защите:** задержать сохранение и показать, что подтверждение не приходит раньше успешного завершения; затем проверить поздний отказ.
