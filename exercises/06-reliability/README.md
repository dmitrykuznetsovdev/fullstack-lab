**До старта:** этап 5; приложение React + TypeScript + MobX + Rspack / NestJS + TypeScript с БД. Решение продолжает `exercises/solutions/app/`. Наставник выбирает с ученицей поддерживаемую библиотеку входа, объясняет настройку по официальной документации, сессию, cookie и выход; итоговую интеграцию пишет ученица. ## 6.1 — Кто может отменить запись

**Задача.** Добавить вход и отмену `DELETE /bookings/:id`, переводящую запись в `cancelled`. Пользователь определяется по проверенной сервером сессии. В `POST /bookings` теперь допускается только `{sessionId}`; присланный `userId` отклоняется как `400 INVALID_INPUT`. Это намеренное изменение учебного контракта: обновить клиент, документацию и тесты вместе.

В NestJS guard проверяет вход и передаёт проверенную личность в обработчик; service проверяет владельца конкретной записи. DTO и ValidationPipe сохраняют отказ лишнему `userId`; UI и MobX store не являются границей доступа. Объяснить guard, pipe и service как разные части пути запроса, подтвердить ответы через HTTP-тесты. Отказ guard не должен случайно менять предусмотренный `401` на стандартный `403`.

| Сценарий отмены | Ответ и данные |
| --- | --- |
| Нет действующей сессии | `401`; изменений нет |
| Своя активная запись | `204`; запись отменена, место свободно |
| Своя уже отменённая запись | `204`; дополнительного изменения нет |
| Чужая или неизвестная запись | `404`; изменений нет |

**Сдать:** вход/выход, серверную проверку владельца, интеграционные тесты с двумя пользователями и Playwright-сценарий «войти → записаться → отменить». Сессии тестовых пользователей создаются через выбранное решение входа, без отключения проверки доступа.

**Приёмка:**
- Чужую запись нельзя изменить прямым HTTP-запросом, даже если убрать ограничения UI.
- После выхода/истечения сессии запрос отклоняется; фиктивный `userId` не позволяет действовать от другого имени.
- Повторная отмена не создаёт лишних мест; после отмены можно записаться снова.
- Наставник проверяет настройки cookie и защиту изменяющих запросов от CSRF для выбранной схемы; ученик объясняет механизм. Проверены межсайтовый запрос без нужной защиты и обычный запрос приложения.

**Изменение на защите:** третий пользователь пытается отменить запись второго: получить тот же отказ без добавления частного условия по id.

## 6.2 — Чистый запуск и учебный выпуск

**Задача.** Настроить команды установки, проверки типов, тестов и production-сборки. В GitHub Actions выполнять их на PR; для интеграционных тестов поднимать отдельную PostgreSQL с фиктивными данными. С наставником подготовить Docker Compose или равнозначную воспроизводимую локальную среду.

Проверять обе части: frontend — tsc, Vitest и Rspack build; backend — проверка типов, NestJS build, Jest/Supertest. Запустить собранный backend и просмотр собранного frontend на локальном стенде, пройти основной сценарий с реальной БД. Dev proxy Rspack не переносится автоматически в production: описать адрес API/маршрутизацию отдельно. После выхода обновить данные входа и доступные действия в MobX store, подтвердив отказ и на сервере.

**Сдать:** workflow, README запуска, `.env.example` только с фиктивными значениями и один проверенный учебный выпуск. Цель по умолчанию — локальный изолированный стенд; внешнюю площадку и возможные расходы сначала выбираем с владельцем. Локальный запуск не называем публичным деплоем.

**Приёмка:**
- Напарник запускает чистую копию по инструкции, применяет миграции и проходит основной сценарий.
- CI действительно падает на временно внесённой неверной проверке и проходит после её исправления; примеры падения не остаются в итоговой ветке.
- Ученик находит лог конкретного шага; в CI нет зависимости от его компьютера или личных секретов.
- Ошибка конфигурации выводит понятное сообщение без пароля и session token.
- Описаны версия выпуска и способ вернуться к предыдущему коду; отдельно указано, что откат кода сам по себе не откатывает схему БД.

**Изменение на защите:** убрать обязательную переменную подключения в локальной пробе, найти причину по диагностике и восстановить запуск.

## 6.3 — Разобрать инцидент без переписывания приложения

**Задача.** В локальной учебной среде остановить только принадлежащую заданию БД, оставив API запущенным. Выполнить просмотр и запись. Зафиксировать время, HTTP-ответ, сообщение UI и серверную ошибку. Затем восстановить БД и проверить приложение.

Требование: ошибка зависимости не превращается в пустой список или успешную запись; ответ `503` с `STORAGE_UNAVAILABLE`, UI предлагает повторить попытку. Для сопоставления запроса и серверного события использовать request id, не пользовательские секреты. Не добавлять слепые автоматические повторы записи.

**Сдать:** `learning/6.3.md` в формате «симптом → гипотеза → проверка → причина → исправление → восстановление» и минимальную необходимую правку с регрессионной проверкой. Если обработка уже корректна, описать доказательство без искусственного изменения кода.

**Приёмка:**
- Наблюдался реальный отказ подключения к учебной БД, не только подмена функции.
- После восстановления данные сохранены, новая запись работает; нет зависших загрузок и утечки внутреннего текста ошибки клиенту.
- Ученик различает тест подмены, интеграционную проверку и наблюдение живого стенда.
- Созданные для демонстрации процессы/контейнеры остановлены, временная конфигурация восстановлена; чужие процессы не тронуты.

**Изменение на защите:** вместо остановки БД временно указать неверный порт API в клиенте; по браузерной диагностике отличить этот сбой от `503` работающего сервера.
