# Fullstack Lab

Учимся full-stack разработке в двух режимах: новый механизм ученица осваивает собственной малой пробой с AI-наставником; подтверждённый может применять через ограниченную реализацию агента. Ученица отвечает за требования, чтение diff, проверки, объяснение поведения и самостоятельное изменение на защите.

**Цель:** уметь довести небольшую пользовательскую задачу от уточнения требований до работающего интерфейса, API, базы данных и проверяемого результата.

**Статус обучения и текущая задача:** [единый прогресс](progress/README.md). Подготовлены 24 задания для восьми этапов; сданы первые работы этапа 0, приложения пока нет. Первая итерация — full-stack база на 26 недель с подготовкой к дальнейшему углублению backend. Подтверждены 8–10 часов в неделю; фактическая трудоёмкость и навыки ещё не оценены, продукт не выбран. Стек задан владельцем; [срез вакансий от 29 сентября 2026 года](docs/job-market-2026-09-29.md) остаётся историческим обоснованием общих навыков.

## Как начать

1. Вместе прочитать план и обсудить доступное время, опыт, интересы и ожидания от обучения.
2. Выполнить задание `0.1` из [этапа 0](exercises/00-workflow/README.md) — сделать первый учебный PR.
3. Двигаться по одному небольшому заданию. Новую тему закреплять изменением условий, а не только повторением примера.
4. После каждого этапа провести демонстрацию и проверить критерии перехода.

Навигация: [задания по этапам](exercises/README.md) · [прогресс и журнал](progress/README.md) · [чтение](docs/reading.md) · [инструкции агентам](AGENTS.md) · [скилл наставника](.ai/skills/fullstack-mentor/SKILL.md). Условия заданий готовы; решения ученица добавляет отдельными PR.

## Направление и обязательный стек

Начинаем с **full-stack веб-разработки на JavaScript и TypeScript**. Один язык на клиенте и сервере уменьшает количество переключений; браузер позволяет быстро увидеть результат, а сервер и база данных дают понимание системы целиком.

Обязательная последовательность — **JavaScript → TypeScript**; frontend — **React + TypeScript + MobX + Rspack**; backend — **NestJS + TypeScript на Node.js**. После этапа 3 обсуждаем малый предметный сценарий того же приложения; после первого выпуска оцениваем самостоятельность, пробелы и задачи для дальнейшего углубления backend. Возможные следующие полгода — гипотеза, Go или Python сейчас не выбираем и переход через шесть месяцев не обещаем. Это не обещание самого лёгкого трудоустройства.

Целевой рынок — Москва и удалённая работа по России. Для первой работы рассматриваем стажировки frontend/Node.js, junior frontend/backend и junior fullstack. Fullstack — ширина обучения, а первое место может требовать более узкой специализации. До выбора стажировки проверяем ограничения по образованию, студенческому статусу и полной занятости. Подробнее — [выводы исследования](docs/job-market-2026-09-29.md).

| Область | Выбор | Когда и зачем |
| --- | --- | --- |
| Основы веба | HTML, CSS, JavaScript, инструменты разработчика в браузере | Сначала понять страницу, события, данные и запросы |
| Типы и модули | TypeScript | После практики JavaScript: описывать данные и обнаруживать ошибки до запуска |
| Интерфейс | React + TypeScript + MobX | После DOM: компоненты и props, локальное состояние, затем общий store, observable/computed/action и обновление UI через observer |
| Сборка frontend | Rspack | На этапе 3: точка входа, TSX/CSS, dev server и production-сборка; проверка типов запускается отдельно |
| Сервер | NestJS + TypeScript на Node.js, HTTP/JSON API | На этапе 4: module → controller → service/provider → хранилище; DTO, pipes, DI и ошибки |
| Хранение | PostgreSQL, сначала SQL напрямую | Понять связи, ограничения и транзакции до добавления ORM |
| Проверки | node:assert/strict → Vitest для frontend; Jest + Supertest для NestJS; позже Playwright | Проверять правила, stores, HTTP-контракт и ключевые пользовательские сценарии |
| Совместная работа | Git, Pull Requests; локальные этапы/эпики и задания, Issues при необходимости | Небольшие изменения и ревью; учебный статус ведём только в progress/README.md |
| Доставка | GitHub Actions; Docker после освоения локального запуска | Воспроизводимые проверки и учебное развёртывание |

MobX, Rspack и NestJS входят в обязательную практику. Сначала понять базовый механизм, затем применить инструмент: React state до MobX, TypeScript до преобразования TSX, HTTP до NestJS. Next.js/SSR и интеграцию ORM можно обсуждать по задаче после первой итерации; они не заменяют обязательный стек. Rspack собирает клиент, NestJS использует собственные команды сборки сервера.

Используем npm как один менеджер пакетов. При создании первого исполняемого задания выберем поддерживаемую LTS-версию Node.js, совместимые версии инструментов и зафиксируем их вместе с lock-файлом и инструкцией запуска.

На старте достаточно одного приложения и одной базы. Микросервисы, Kubernetes, несколько frontend-фреймворков и самостоятельное обучение моделей в начальную программу не входят. Нужные инструменты добавляем после появления конкретной задачи.

## Что должно остаться в голове

- **Код:** значения и типы, условия, циклы, функции, параметры, возвращаемые значения, коллекции, модули, ошибки и асинхронность.
- **Данные:** где хранится состояние, кто может его менять, как отличить отсутствие значения от нуля, как предотвратить дубликаты.
- **Веб:** что происходит между действием в браузере, запросом, сервером, базой и ответом; чем клиентская проверка отличается от серверной.
- **Диагностика:** воспроизвести проблему, прочитать сообщение, поставить breakpoint, сформулировать и проверить гипотезу.
- **Качество:** проверять результат по требованиям, включая ошибочные входы, пустые состояния и сбои зависимостей.
- **Командная работа:** задавать предметные вопросы, читать diff, объяснять решение, принимать замечания и обозначать неизвестное.

Синтаксис можно подсмотреть. Объяснить поведение, предсказать результат и сделать небольшое изменение нужно уметь самостоятельно.

## Темп и формат

Подтверждённый бюджет — **8–10 часов в неделю**, за **26 недель — 208–260 часов**, включая чтение, код, разборы, исправления, повторение и проверки. Один разбор на 45–60 минут — рабочий формат внутри этих часов. В горизонте **24 недели основной практики + 2 недели резерва**; дата начала ещё не назначена. Это плановый бюджет, не обещание освоения или трудоустройства: фактическую трудоёмкость ещё не измеряли.

После первых двух недель калибруем темп по реально затраченному времени, законченному результату, объяснению, изменению на защите и помощи. Если работа ещё на этапе 0, используем её реальные результаты, не предполагаем принятие 1.1. При отставании уменьшаем шаг и необязательный объём, используем резерв; его можно взять раньше со сдвигом блоков и уменьшением остатка внутри тех же 26 недель. Неиспользованный резерв — на повторение и перенос навыка, без новых технологий. Если обязательные критерии не помещаются даже после этого, вместе пересматриваем объём/нагрузку и честно переносим незакрытую часть за горизонт, фиксируя реальное состояние на 26-й неделе. Критерии и самостоятельность по дате не ослабляем.

Пример недели: несколько самостоятельных занятий, один законченный результат, ревью и короткое повторение без генерации готового решения. Часть времени выделяем на чтение документации и технический английский; переводчик допустим, но ключевые термины учимся узнавать.

Переход определяется навыком. Если критерий не выполнен, уменьшаем задачу, разбираем затруднение и пробуем похожий пример. Календарь не заменяет понимание.

Для каждого этапа подготовлены [три задания](exercises/README.md): создание результата, работа с ошибкой или существующим кодом, перенос навыка на изменённые требования. Это практика внутри указанных сроков. Первые проверки используют `node:assert/strict`, на этапе 3 — Vitest для функций и MobX stores, на этапе 4 — Jest и Supertest для NestJS. SQL-конкурентность — на этапе 5, guards/авторизация и Playwright — на этапе 6. Крупные задания делим на малые результаты внутри прежних ID. Горизонт сокращён прежде всего за счёт продолжения готовой основы на этапе 7 вместо нового большого проекта; темп проверяем по фактической работе.

В этапах 1–3 закрепляем чтение кода, базовые алгоритмы и оценку числа операций на понятных коллекциях. Во frontend обязательно проходим loading/error/empty-состояния, гонки запросов, формы, клавиатуру и адаптивность. С этапа 4 постепенно повышаем самостоятельность работы с API, логами и существующей реализацией.

### Как усложняем задания

Сначала делаем простой работающий вариант. Затем меняем одно условие: пустой список, неверный ввод, повторный клик, недоступный сервер или изменение формата данных. Позже добавляем чужой код и намеренно внесённые дефекты.

На каждом этапе есть четыре вида практики: написать небольшой фрагмент, прочитать существующий, найти причину ошибки и изменить требование. Один большой сгенерированный проект не заменяет эти упражнения.

## Как используем ИИ

Разделяем освоение новой темы и применение уже знакомой.

| Ситуация | Что делаем |
| --- | --- |
| Новое понятие | Сначала собственная попытка и прогноз результата; у ИИ просим объяснение, вопрос или небольшую подсказку |
| Непонятная ошибка | Записываем ожидаемое и фактическое поведение, читаем сообщение, проверяем хотя бы одну гипотезу; затем подключаем ИИ |
| Подтверждённый механизм | Ученица задаёт ограниченные требования и ожидаемые проверки; агент может реализовать знакомую часть, настройку и тесты. Ученица читает diff, проверяет и защищает результат |
| Проверка усвоения | Решаем короткую изменённую задачу без генерации ответа; документация разрешена |
| Ревью | ИИ помогает искать вопросы и риски; ученик и наставник проверяют выводы по коду и выполненным проверкам |

Перед запросом полезно записать: «что хочу получить», «что уже знаю», «что пробовал» и «как проверю ответ». Если совсем непонятно, с чего начать, допустимо сразу попросить разложить задачу на шаги без готовой реализации.

В PR коротко отмечаем, где помог ИИ, что проверено самостоятельно и что осталось непонятным. Не требуется публиковать историю переписки. Утверждение модели «всё работает» не считается проверкой; тесты, написанные моделью, тоже сверяем с требованиями.

Перед делегированием подтверждаем конкретный механизм: объяснение + собственная малая проба или изменение + наблюдаемая проверка. При новом механизме AI не выдаёт готовую изучаемую часть или полный набор тестов; короткий пример на других данных и постепенные подсказки допустимы. Для освоенного разрешена ограниченная реализация, знакомая настройка и тесты агента. В смешанной задаче новая часть сначала проходит собственную пробу. Если сгенерированное непонятно, возвращаемся к малому примеру; зелёный CI и объяснение агента не принимают задание. На защите — малое изменение без готовой генерации, документация разрешена. Искусственный срок без AI и долю ручного кода не задаём. Подробный порядок — в [скилле наставника](.ai/skills/fullstack-mentor/SKILL.md).

## Как работаем вдвоём

**Ученик** уточняет задачу, предлагает короткий план, делает небольшое изменение, проверяет результат и готовит демонстрацию. При затруднении сообщает, что ожидал, что получил и что уже проверил.

**Наставник** подбирает посильные задачи, объясняет ход рассуждений, помогает проверить гипотезы и проводит ревью. Новый механизм ученица проверяет сама; после подтверждения агент может реализовать ограниченную знакомую часть. Намеренно дефектный небольшой фрагмент для диагностики допустим; при новом механизме готового исправления за ученицу не даём. Помощь фиксируем предметно: что сделал агент и что ученица объяснила, проверила и изменила сама.

Обычный цикл:

1. **Задание:** проблема пользователя, ожидаемое поведение, ограничения и критерии приёмки; Issue можно связать с его номером.
2. **Ветка:** одна задача — одна ветка, например `learn/01-available-sessions`.
3. **PR:** что изменено, как запустить, что проверено, помощь ИИ и открытые вопросы.
4. **Ревью и демонстрация:** обсуждаем поведение и доказательства, исправляем замечания.
5. **Merge и короткая заметка:** что стало понятнее и что стоит повторить.

Это договорённость о процессе; обязательное ревью и запрет прямого push пока не настроены технически.

### Когда учебная задача завершена

- [ ] Критерии приёмки выполнены; невыполненные пункты явно обозначены.
- [ ] Есть понятная инструкция запуска или просмотра результата.
- [ ] Проверены обычный сценарий, подходящая граница и существенная ошибка ввода либо сбой.
- [ ] Для изменения поведения добавлена уместная проверка; исправление ошибки подтверждено воспроизведением.
- [ ] Ученик объясняет путь данных и может сделать небольшое изменение без готового ответа ИИ.
- [ ] В diff нет случайных файлов, секретов и чужих данных.
- [ ] Замечания наставника разобраны; остаточные ограничения описаны.

Для заметки или простой правки документации достаточно проверки текста, ссылок и diff. Автотесты ради самого факта наличия тестов не нужны.

## Предварительная идея совместного проекта

**Сервис записи на занятия или бронирования небольшого ресурса.** Например, расписание клуба или мастерской на вымышленных данных. Эта тема позволяет пройти интерфейс, сервер, хранение, права и конкурентные изменения в одном понятном сценарии.

Это кандидат, а не утверждённый продукт. После этапа 3 выберем тему вместе: нужен доступный для общения пользователь, понятная проблема, небольшой первый сценарий и возможность получать обратную связь. На этапе 7 завершим один малый срез на этой основе. При другом сюжете сохраняем сопоставимые требования к данным, серверным правилам и правам; новый стек и повторная настройка в финал не входят.

Предполагаемые границы первого продукта:

- Участник видит занятия и свободные места, записывается и отменяет свою запись.
- Организатор меняет доступность занятия в ограниченном итоговом сценарии.
- Сервер проверяет права, допустимость операции и количество мест.
- Данные сохраняются; пользователь понимает состояния загрузки, ошибки и успеха.

Развиваем продукт вертикальными срезами: каждый срез даёт законченный сценарий через нужные части системы.

| Срез | Результат | Что обязательно проверить |
| --- | --- | --- |
| 1. Просмотр | Список из базы через API отображается в браузере | Нет данных, ошибка сервера, повторная загрузка |
| 2. Запись | Пользователь занимает место и видит свою запись | Нет свободных мест, некорректный запрос, повторное действие |
| 3. Доступ | Вход, свои записи, действия организатора | Запрос без входа и попытка изменить чужую запись, в том числе напрямую через API |
| 4. Надёжность | Ограничения и транзакции защищают бронирование | Два одновременных запроса на последнее место: подтверждена только одна запись |
| 5. Учебный выпуск | Проверки в CI, инструкция, развёртывание и обратная связь | Запуск с чистой копии, сохранность данных, понятный сценарий восстановления |

До реализации и проверки доступа используем только изолированную учебную среду и вымышленных участников. Для входа используем поддерживаемое решение, выбранное на соответствующем этапе; собственную криптографию не разрабатываем. Учебную публикацию отделяем от запуска для реальных пользователей.

Платежи, чат, мобильное приложение, маркетплейс и ИИ-функции в первый продукт не входят. Более крупный проект вырастает из работающего небольшого продукта и реальных потребностей.


У каждого этапа есть README с тремя заданиями. [Короткие разборы](examples/README.md) помогают обсуждать механизмы без готовых решений. Каталогов `project/` и `docs/decisions/` сейчас нет. Решения и заметки появляются по мере учебной работы в двух режимах; единственная будущая основа этапов 3–7 — `exercises/solutions/app/`, `web/` затем `api/`. `project/` не обязателен: более поздний перенос выполняется одним перемещением с обновлением CI/инструкций, без второй копии. Тему обсуждаем после этапа 3. Не создаём готовое приложение для заполнения структуры. Корневой документ — источник плана, `exercises/` — условий, [progress/README.md](progress/README.md) — учебного состояния. История изменений сохраняется в Git и PR.

Репозиторий публичный. Используем вымышленные учебные данные; токены, пароли, реальные персональные сведения и материалы закрытых рабочих проектов не публикуем. До первого исполняемого задания добавим `.gitignore` для зависимостей, сборок и локальных файлов окружения, а в примерах окружения оставим только фиктивные значения.

## Как оцениваем прогресс

После проверки отмечаем в [едином прогрессе](progress/README.md) уровень самостоятельности: **с пошаговой помощью → с подсказками → самостоятельно → может объяснить и перенести на новую задачу**. Фиксируем конкретный пример и доказательство, а не общую оценку «всё понял». Там же находятся текущая задача, затруднения, следующий шаг и краткий журнал для возвращения после перерыва. Заметки решения содержат подробные наблюдения, а PR/Issues дают ссылки; параллельные ручные таблицы статуса не ведём.

Смотрим на пять результатов: уточнение задачи, чтение кода, самостоятельное изменение, диагностика и проверка. Количество строк, пройденных видео и сгенерированных экранов не является мерой освоения.

Контрольные точки:

- **После двух недель:** подходит ли темп, где не хватает базы, сохраняется ли интерес к самостоятельной работе.
- **После этапа 3:** проверенные JS/браузер/React-переходы, готовность к серверу и малый предметный сценарий той же основы.
- **После этапа 6:** самостоятельная задача с незнакомой ошибкой и проверкой доступа или данных.
- **После первого выпуска проекта:** владение задачей, независимое изменение на защите, пробелы для следующего backend-углубления и соответствие конкретным вакансиям. Это не обязательный переход на второй язык.

Регион и формат определены: Москва, также удалённая работа по России. Срок поиска, образование и доступная занятость ученика пока неизвестны. После этапа 3 снова сверяемся с актуальными вакансиями; после этапа 6 проводим пробное собеседование по коду проекта. Не ждём знания всех технологий: готовность к конкретной стажировке проверяем отдельно. Полнота маршрута сама по себе не означает готовность к любой junior-вакансии.

### Почему разделяем получение результата и обучение

В эксперименте Anthropic с освоением новой библиотеки группа с ИИ хуже выполнила последующую проверку знаний; это ограниченный эксперимент, а не доказательство вреда любых способов использования ИИ. Метаанализ исследований программирования также не обнаружил устойчивого общего улучшения результатов обучения от самого наличия ИИ. Поэтому в нашем плане есть самостоятельные попытки, объяснение решений и перенос навыка на изменённую задачу. Это наш методический выбор, а не обещание универсальной эффективности.

- [Anthropic: How AI assistance impacts the formation of coding skills, 2026](https://www.anthropic.com/research/AI-assistance-coding-skills).
- [A meta-analysis of the effect of generative AI on productivity and learning in programming, препринт 2026](https://arxiv.org/abs/2605.04779).

План пересматриваем по результатам работы. Первое действие после его принятия — учебное задание `0.1` и первый PR ученика.
