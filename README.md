# Fullstack Lab

Учимся full-stack разработке вдвоём: ученик решает задачи, наставник помогает разобраться, проводит ревью и постепенно передаёт больше самостоятельности. Используем ИИ с самого начала, одновременно учимся понимать, изменять и проверять код.

**Цель:** уметь довести небольшую пользовательскую задачу от уточнения требований до работающего интерфейса, API, базы данных и проверяемого результата.

**Статус:** стартовый план для обсуждения. Приложения и выполненных упражнений пока нет. Направление — разработка веб-приложений; конкретный продукт и темп уточним по результатам первых этапов.

## Как начать

1. Вместе прочитать план и обсудить доступное время, опыт, интересы и ожидания от обучения.
2. Выполнить задание `00` из раздела «Первые задания» — сделать первый учебный PR.
3. Двигаться по одному небольшому заданию. Новую тему закреплять изменением условий, а не только повторением примера.
4. После каждого этапа провести демонстрацию и проверить критерии перехода.

Сейчас весь план находится в этом README. Папки и дополнительные документы создаём тогда, когда для них появляется содержимое.

## Предполагаемое направление и стек

Начинаем с **full-stack веб-разработки на JavaScript и TypeScript**. Один язык на клиенте и сервере уменьшает количество переключений; браузер позволяет быстро увидеть результат, а сервер и база данных дают понимание системы целиком.

Это учебная гипотеза, а не обещание самого лёгкого трудоустройства. После первых трёх этапов решим, где ученику интереснее углубляться: в интерфейсах или в серверной части. Общую базу и умение провести задачу через весь стек сохраняем.

| Область | Начальный выбор | Когда и зачем |
| --- | --- | --- |
| Основы веба | HTML, CSS, JavaScript, инструменты разработчика в браузере | Сначала понять страницу, события, данные и запросы |
| Типы и модули | TypeScript | После практики JavaScript: описывать данные и обнаруживать ошибки до запуска |
| Интерфейс | React + Vite | После обычного DOM: компоненты, состояние, формы и взаимодействие с API |
| Сервер | Node.js + Fastify, HTTP/JSON API | Явно проследить запрос, валидацию, бизнес-правило и ответ |
| Хранение | PostgreSQL, сначала SQL напрямую | Понять связи, ограничения и транзакции до добавления ORM |
| Проверки | Vitest; позже Playwright | Проверять логику и несколько ключевых пользовательских сценариев |
| Совместная работа | Git, GitHub Issues и Pull Requests | Небольшие изменения, ревью и история решений |
| Доставка | GitHub Actions; Docker после освоения локального запуска | Воспроизводимые проверки и учебное развёртывание |

Используем npm как один менеджер пакетов. При создании первого исполняемого задания выберем поддерживаемую LTS-версию Node.js, совместимые версии инструментов и зафиксируем их вместе с lock-файлом и инструкцией запуска.

На старте достаточно одного приложения и одной базы. Микросервисы, Kubernetes, несколько frontend-фреймворков и самостоятельное обучение моделей в начальную программу не входят. Нужные инструменты добавляем после появления конкретной задачи.

## Что должно остаться в голове

- **Код:** значения и типы, условия, циклы, функции, параметры, возвращаемые значения, коллекции, модули, ошибки и асинхронность.
- **Данные:** где хранится состояние, кто может его менять, как отличить отсутствие значения от нуля, как предотвратить дубликаты.
- **Веб:** что происходит между действием в браузере, запросом, сервером, базой и ответом; чем клиентская проверка отличается от серверной.
- **Диагностика:** воспроизвести проблему, прочитать сообщение, поставить breakpoint, сформулировать и проверить гипотезу.
- **Качество:** проверять результат по требованиям, включая ошибочные входы, пустые состояния и сбои зависимостей.
- **Командная работа:** задавать предметные вопросы, читать diff, объяснять решение, принимать замечания и обозначать неизвестное.

Синтаксис можно подсмотреть. Объяснить поведение, предсказать результат и сделать небольшое изменение нужно уметь самостоятельно.

## Темп и формат

Рабочее предположение — **8–12 часов в неделю** и один разбор с наставником на 45–60 минут. Это ещё не согласованный график ученика. Ориентир на весь маршрут — примерно **6–9 месяцев**, с корректировкой после первых двух недель. Это не срок гарантированного выхода на работу.

Пример недели: несколько самостоятельных занятий, один законченный результат, ревью и короткое повторение без генерации готового решения. Часть времени выделяем на чтение документации и технический английский; переводчик допустим, но ключевые термины учимся узнавать.

Переход определяется навыком. Если критерий не выполнен, уменьшаем задачу, разбираем затруднение и пробуем похожий пример. Календарь не заменяет понимание.

## Маршрут обучения

Сроки приблизительные. Этапы идут последовательно; тестирование, Git и работа с ИИ продолжаются на всём маршруте.

| Этап | Ориентир | Практический результат | Критерий перехода |
| --- | --- | --- | --- |
| 0. Среда и первая совместная работа | 1 неделя | Первый PR с учебной заметкой, запуск простого файла, знакомство с браузерной консолью | Сам клонирует репозиторий, создаёт ветку, коммит и PR; понимает diff и умеет вернуть свою незакоммиченную правку |
| 1. Основы JavaScript | 3–4 недели | Небольшие программы для фильтрации, расчётов и преобразования данных | Объясняет функцию, самостоятельно меняет условие и находит ошибку; проверяет обычный и граничный случаи |
| 2. HTML, CSS и браузер | 3–4 недели | Страница списка занятий с фильтром и формой на локальных данных | Страница работает на узком экране и с клавиатуры; ученик понимает DOM, события и место хранения состояния |
| 3. TypeScript и React | 3–4 недели | Тот же интерфейс на компонентах с типизированными данными | Сам меняет форму и состояние; различает ошибку типов и ошибку выполнения; объясняет передачу данных между компонентами |
| 4. HTTP и backend | 3–4 недели | API списка занятий и записей с временным хранением в памяти, подключённый к интерфейсу | Прослеживает запрос от браузера до обработчика; проверяет входные данные и ошибки; понимает потерю данных при перезапуске |
| 5. SQL и PostgreSQL | 3–4 недели | Постоянное хранение, миграции и интеграционные проверки API | Пишет SELECT и JOIN, объясняет ключи и ограничения; данные переживают перезапуск; запросы параметризованы |
| 6. Надёжность и доставка | 3–4 недели | Проверки в CI, вход и права доступа, учебное развёртывание | Чистая копия запускается по инструкции; чужие записи защищены на сервере; можно воспроизвести сбой и откатить своё изменение |
| 7. Совместный проект | 6–10 недель | Небольшой продукт с согласованным пользователем, обратной связью и последовательными релизами | Ученик ведёт ограниченную задачу через весь стек, объясняет проверки и исправляет замечания ревью |

### Как усложняем задания

Сначала делаем простой работающий вариант. Затем меняем одно условие: пустой список, неверный ввод, повторный клик, недоступный сервер или изменение формата данных. Позже добавляем чужой код и намеренно внесённые дефекты.

На каждом этапе есть четыре вида практики: написать небольшой фрагмент, прочитать существующий, найти причину ошибки и изменить требование. Один большой сгенерированный проект не заменяет эти упражнения.

## Первые задания

Это задания для будущих учебных PR, а не список уже выполненных работ. Каждый пункт превращаем в отдельную задачу после принятия плана. Наставник не публикует готовое решение до самостоятельной попытки ученика.

### 00 — Первый учебный PR

**Задача:** создать `learning/00-start.md` с доступным графиком, целями на первые две недели, тремя вопросами и описанием одной знакомой бытовой задачи, которую хотелось бы автоматизировать. Личные и рабочие конфиденциальные сведения не нужны.

**Приёмка:** отдельная ветка и PR; ученик может объяснить каждую строку diff, внести одну правку по ревью и описать разницу между коммитом, push и merge. Способ участия — приглашение в репозиторий или fork — выбираем после получения GitHub-логина ученика.

### 01 — Найти свободные занятия

**Задача:** в `exercises/01-available-sessions/` реализовать функцию `getAvailableSessions(sessions, minPlaces)`. У занятия есть `id`, `title` и целочисленное `freePlaces >= 0`. `minPlaces` — целое число больше нуля. Функция возвращает занятия с `freePlaces >= minPlaces`, сохраняя порядок и не изменяя входной массив. При некорректном `minPlaces` выбрасывает `RangeError`; на этом шаге данные занятий считаем валидными.

**Приёмка:** проверить пустой список, отсутствие подходящих занятий, ровно нужное число мест, несколько результатов, неизменность входа и ошибочные значения `minPlaces`. Ученик объясняет параметры, возвращаемое значение и условие фильтрации. После обсуждения самостоятельно меняет одно правило. Для этого задания достаточно проверок через встроенный `node:assert/strict`; тестовый фреймворк вводим позже.

### 02 — Прочитать и исправить

**Задача:** наставник готовит небольшой пример с ошибкой границы или непреднамеренным изменением массива. Ученик сначала описывает ожидаемое поведение и воспроизводит дефект, затем исправляет причину.

**Приёмка:** есть вход, на котором исходный вариант ошибается; проверка не проходит до исправления и проходит после. Ученик объясняет причину и показывает, что исправление не сломало соседний случай.

### 03 — Страница списка занятий

**Задача:** в `exercises/03-sessions-page/` сделать HTML/CSS/JavaScript-страницу на вымышленных данных: название, количество мест, фильтр и сообщение об отсутствии результатов.

**Приёмка:** подписи полей доступны, фильтр работает с клавиатуры, страница помещается на экране шириной 360 px, пустое состояние понятно. Ученик показывает обработчик события и самостоятельно меняет отображаемое поле. React и backend для этого задания не требуются.

## Как используем ИИ

Разделяем освоение новой темы и применение уже знакомой.

| Ситуация | Что делаем |
| --- | --- |
| Новое понятие | Сначала собственная попытка и прогноз результата; у ИИ просим объяснение, вопрос или небольшую подсказку |
| Непонятная ошибка | Записываем ожидаемое и фактическое поведение, читаем сообщение, проверяем хотя бы одну гипотезу; затем подключаем ИИ |
| Знакомая задача | Можно генерировать код и заготовки тестов, затем читать diff и проверять поведение |
| Проверка усвоения | Решаем короткую изменённую задачу без генерации ответа; документация разрешена |
| Ревью | ИИ помогает искать вопросы и риски; ученик и наставник проверяют выводы по коду и выполненным проверкам |

Перед запросом полезно записать: «что хочу получить», «что уже знаю», «что пробовал» и «как проверю ответ». Если совсем непонятно, с чего начать, допустимо сразу попросить разложить задачу на шаги без готовой реализации.

В PR коротко отмечаем, где помог ИИ, что проверено самостоятельно и что осталось непонятным. Не требуется публиковать историю переписки. Утверждение модели «всё работает» не считается проверкой; тесты, написанные моделью, тоже сверяем с требованиями.

Запрета на инструменты нет. Есть обязательство понимать существенные изменения и честно показывать границы своей самостоятельности.

## Как работаем вдвоём

**Ученик** уточняет задачу, предлагает короткий план, делает небольшое изменение, проверяет результат и готовит демонстрацию. При затруднении сообщает, что ожидал, что получил и что уже проверил.

**Наставник** подбирает посильные задачи, объясняет ход рассуждений, помогает проверить гипотезы и проводит ревью. Если сложный участок сделал наставник, фиксируем это и отдельно даём ученику небольшую задачу на понимание этого участка.

Обычный цикл:

1. **Issue:** проблема пользователя, ожидаемое поведение, ограничения и критерии приёмки.
2. **Ветка:** одна задача — одна ветка, например `learn/01-available-sessions`.
3. **PR:** что изменено, как запустить, что проверено, помощь ИИ и открытые вопросы.
4. **Ревью и демонстрация:** обсуждаем поведение и доказательства, исправляем замечания.
5. **Merge и короткая заметка:** что стало понятнее и что стоит повторить.

Это договорённость о процессе; обязательное ревью и запрет прямого push пока не настроены технически.

### Когда учебная задача завершена

- [ ] Критерии приёмки выполнены; невыполненные пункты явно обозначены.
- [ ] Есть понятная инструкция запуска или просмотра результата.
- [ ] Проверены обычный сценарий, подходящая граница и существенная ошибка ввода либо сбой.
- [ ] Для изменения поведения добавлена уместная проверка; исправление ошибки подтверждено воспроизведением.
- [ ] Ученик объясняет путь данных и может сделать небольшое изменение без готового ответа ИИ.
- [ ] В diff нет случайных файлов, секретов и чужих данных.
- [ ] Замечания наставника разобраны; остаточные ограничения описаны.

Для заметки или простой правки документации достаточно проверки текста, ссылок и diff. Автотесты ради самого факта наличия тестов не нужны.

## Предварительная идея совместного проекта

**Сервис записи на занятия или бронирования небольшого ресурса.** Например, расписание клуба или мастерской на вымышленных данных. Эта тема позволяет пройти интерфейс, сервер, хранение, права и конкурентные изменения в одном понятном сценарии.

Это кандидат, а не утверждённый продукт. После этапа 3 выберем тему вместе: нужен доступный для общения пользователь, понятная проблема, небольшой первый сценарий и возможность получать обратную связь. На этапе 7 уточним требования и превратим их в задачи. Другую предметную область можно выбрать, сохранив учебные цели.

Предполагаемые границы первого продукта:

- Участник видит занятия и свободные места, записывается и отменяет свою запись.
- Организатор создаёт занятие и меняет его доступность.
- Сервер проверяет права, допустимость операции и количество мест.
- Данные сохраняются; пользователь понимает состояния загрузки, ошибки и успеха.

Развиваем продукт вертикальными срезами: каждый срез даёт законченный сценарий через нужные части системы.

| Срез | Результат | Что обязательно проверить |
| --- | --- | --- |
| 1. Просмотр | Список из базы через API отображается в браузере | Нет данных, ошибка сервера, повторная загрузка |
| 2. Запись | Пользователь занимает место и видит свою запись | Нет свободных мест, некорректный запрос, повторное действие |
| 3. Доступ | Вход, свои записи, действия организатора | Запрос без входа и попытка изменить чужую запись, в том числе напрямую через API |
| 4. Надёжность | Ограничения и транзакции защищают бронирование | Два одновременных запроса на последнее место: подтверждена только одна запись |
| 5. Учебный выпуск | Проверки в CI, инструкция, развёртывание и обратная связь | Запуск с чистой копии, сохранность данных, понятный сценарий восстановления |

До реализации и проверки доступа используем только изолированную учебную среду и вымышленных участников. Для входа используем поддерживаемое решение, выбранное на соответствующем этапе; собственную криптографию не разрабатываем. Учебную публикацию отделяем от запуска для реальных пользователей.

Платежи, чат, мобильное приложение, маркетплейс и ИИ-функции в первый продукт не входят. Более крупный проект вырастает из работающего небольшого продукта и реальных потребностей.

## Как будет расти репозиторий

Планируемая структура, которую создаём постепенно:

```text
README.md          — направление и текущий учебный маршрут
learning/          — короткие заметки и итоги этапов
exercises/         — самостоятельные задания с условиями и проверками
project/           — совместное приложение, когда выбрана тема
docs/decisions/    — решения по проекту: контекст, выбор и последствия
```

У каждого исполняемого задания будет собственный README с условиями, запуском и проверками. Корневой документ остаётся навигацией и источником актуального плана; историю изменений сохраняем в Git и PR.

Репозиторий публичный. Используем вымышленные учебные данные; токены, пароли, реальные персональные сведения и материалы закрытых рабочих проектов не публикуем. До первого исполняемого задания добавим `.gitignore` для зависимостей, сборок и локальных файлов окружения, а в примерах окружения оставим только фиктивные значения.

## Как оцениваем прогресс

После каждого этапа отмечаем уровень самостоятельности: **с пошаговой помощью → с подсказками → самостоятельно → может объяснить и перенести на новую задачу**. Фиксируем конкретный пример, а не общую оценку «всё понял».

Смотрим на пять результатов: уточнение задачи, чтение кода, самостоятельное изменение, диагностика и проверка. Количество строк, пройденных видео и сгенерированных экранов не является мерой освоения.

Контрольные точки:

- **После двух недель:** подходит ли темп, где не хватает базы, сохраняется ли интерес к самостоятельной работе.
- **После этапа 3:** выбор большего уклона во frontend или backend и обсуждение темы проекта.
- **После этапа 6:** самостоятельная задача с незнакомой ошибкой и проверкой доступа или данных.
- **После первого выпуска проекта:** что получается без наставника, какие пробелы мешают следующей задаче и насколько навыки совпадают с целевыми вакансиями.

Регион, формат работы и сроки поиска пока не определены. Когда они появятся, сравним требования 15–20 подходящих начальных вакансий и стажировок и скорректируем акценты. Полнота маршрута сама по себе не означает готовность к любой junior-вакансии.

### Почему разделяем получение результата и обучение

В эксперименте Anthropic с освоением новой библиотеки группа с ИИ хуже выполнила последующую проверку знаний; это ограниченный эксперимент, а не доказательство вреда любых способов использования ИИ. Метаанализ исследований программирования также не обнаружил устойчивого общего улучшения результатов обучения от самого наличия ИИ. Поэтому в нашем плане есть самостоятельные попытки, объяснение решений и перенос навыка на изменённую задачу. Это наш методический выбор, а не обещание универсальной эффективности.

- [Anthropic: How AI assistance impacts the formation of coding skills, 2026](https://www.anthropic.com/research/AI-assistance-coding-skills).
- [A meta-analysis of the effect of generative AI on productivity and learning in programming, препринт 2026](https://arxiv.org/abs/2605.04779).

План пересматриваем по результатам работы. Первое действие после его принятия — учебное задание `00` и первый PR ученика.
